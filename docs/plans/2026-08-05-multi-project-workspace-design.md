# CodeAtlas v0.2 多项目工作空间设计

- 状态：已确认，进入实施
- 日期：2026-08-05
- 目标版本：0.2.0

## 1. 产品结果

v0.2 的用户结果是：一个 CodeAtlas 工作空间可以登记多个真实项目，只启动一个本地服务，同时查看全部项目、单个项目和项目之间的明确依赖。完整空间图仍然是最终结果；项目筛选只是用户主动选择的观察方式，不能改变底层总量，也不能把筛选后的局部图伪装成完整图。

本阶段不尝试一次解决所有跨语言调用。跨项目边分为两类：CodeGraph 已经给出的项目内部代码事实，以及 CodeAtlas 根据稳定清单生成的项目间依赖。第一版从 `package.json` 包名和依赖开始，生成项目级 `DEPENDS_ON` 边。任何未来的名称匹配、HTTP 路由匹配或 AI 推断都必须使用较低证据等级，不能冒充确定事实。

## 2. 方案选择

评估了三种方案：工作空间根目录单索引、复制合并 SQLite、读取时聚合独立索引。选择第三种。

单索引最省代码，但会受根目录 `.gitignore`、嵌套 Git 仓库和不同项目同步周期影响；此前真实工作空间已经出现“找不到文件”。复制合并数据库能统一查询，却需要维护第二份可损坏的派生数据，并引入事务和迁移成本。读取时聚合让每个项目保留自己的 `.codegraph`，CodeAtlas 只做只读归一化，符合本地优先和适配器边界。

## 3. 工作空间模型

配置升级为 Schema 2：

```json
{
  "schemaVersion": 2,
  "id": "workspace-uuid",
  "name": "commerce",
  "root": ".",
  "initializedAt": "2026-08-05T00:00:00.000Z",
  "projects": [
    { "id": "frontend", "name": "frontend", "path": "apps/frontend" },
    { "id": "api", "name": "api", "path": "services/api" }
  ]
}
```

路径必须相对工作空间根目录，项目必须位于工作空间内部。Schema 1 在加载时迁移为 Schema 2，已有单项目工作空间继续使用 `root` 项目，不要求用户重新初始化。写配置采用临时文件加原子替换，重复添加相同路径会返回明确错误。

CLI 增加 `project add/list/remove`。`init --empty` 创建不包含根项目的聚合工作空间；原有 `init` 行为保持兼容。`status`、`sync` 和 `open` 遍历所有项目，分别报告索引状态；一个项目失败不会掩盖其他项目状态，但 `open` 至少需要一个兼容索引。

## 4. 聚合与查询

每个项目使用自己的绝对根路径读取 CodeGraph 数据库。归一化 ID 增加项目命名空间，例如 `file:frontend:src/App.tsx`、`symbol:api:n-auth`。工作空间节点包含所有项目节点，各项目内部目录、文件和符号保持原有包含关系。

多个项目快照在同一全局节点和边预算下合并。返回值继续同时报告底层总量、实际返回量和截断原因。状态接口增加逐项目 CodeGraph 信息；图查询和搜索接口接受可选 `project` 参数。项目筛选保留工作空间节点和目标项目节点，只返回所选项目内部节点，以及目标项目之间存在的关系。

跨项目依赖适配器读取每个项目的 `package.json`。如果项目 A 的 dependencies、devDependencies、peerDependencies 或 optionalDependencies 包含项目 B 的 package name，则生成 `project:A → project:B` 的 `DEPENDS_ON` 边，来源为 `package.json`，证据类型为 `static-derived`，可信度为 1。无法解析的清单只产生项目状态警告，不中断代码图谱。

## 5. Web 交互

左侧工作空间区域增加项目筛选器。默认选择“全部项目”，显示完整聚合图；用户可以切换到单个项目。筛选状态会出现在标题和状态栏中，避免误解当前范围。每个项目显示名称、索引健康状态以及节点数量。

图谱节点继续按代码类型表达主颜色，同时项目节点使用稳定的项目色；节点详情和悬停卡明确显示所属项目。搜索跟随当前项目筛选，选择搜索结果后仍可展开上下游。返回完整空间时恢复当前视图的全部项目，而不是强制切回某一图类型。

v0.2 不实现可编辑的项目设置页面，项目增删通过 CLI 完成；不实现任意工作空间外路径；不推断方法级跨项目调用。这些限制写入 README、CHANGELOG 和迭代记录。

## 6. 错误处理与测试

工作空间测试覆盖 Schema 1 迁移、相对路径、重复项目、越界路径和原子写入。适配器测试使用两个独立 SQLite fixture，验证 ID 不冲突、总量正确、项目包含边和包依赖边。CLI 测试覆盖 `init --empty`、项目增删列表和多项目状态。API 测试覆盖全部项目、单项目筛选、项目搜索和部分索引不可用。

前端使用组件测试和 Playwright 验证项目切换、范围提示、搜索跟随筛选、完整空间恢复和项目详情。每个阶段执行聚焦测试，最终执行 `npm test`、`npm run typecheck`、`npm run build` 与 `npm run test:e2e`。测试结果、提交和已知限制记录到 `docs/iterations/2026-08-05-v0.2.0.md`。
